# बैच प्रोसेसिंग

<TLDR>फ़ोल्डर कार्य चयन और progress साझा करते हैं, लेकिन लिखने और overwrite के नियम अलग हैं। डिफ़ॉल्ट concurrency एक है। परीक्षण फ़ोल्डर में scope और output देखकर विस्तार करें।</TLDR>

## अवलोकन

Sidebar या file explorer की फ़ोल्डर कार्रवाई में लिंक, अवधारणा, शीर्षक, अनुवाद, मूल अंश, Mermaid और सूत्र सुधार हैं। सामान्य folder research नहीं; title generation शोध जोड़ सकती है। पूरा बैच transaction नहीं है: दूसरे फ़ाइल के failure या cancel पर पूरे outputs रहते हैं।

## काम कैसे होता है

### निष्पादन मॉडल

1. कार्य और केवल इच्छित फ़ाइलों वाला फ़ोल्डर चुनें।
2. extension, selection और उस कार्य के output exclusions लागू होते हैं।
3. कार्य का provider/model चलता और progress, त्रुटि तथा पथ मिलता है।
4. समाप्ति या cancel पर रिपोर्ट/फ़ाइल देखकर फिर चलाएँ।

लिंक, अवधारणा, शीर्षक, मूल अंश, Mermaid और सूत्र सामान्यतः subfolders लेते हैं। **फ़ोल्डर अनुवाद पहले केवल सीधे बच्चे लेता है।** Developer mode और advanced file selection दोनों सक्रिय होने पर profiles scope/filter बदल सकती हैं। वास्तविक चुने फ़ाइल देखें।

### Overwrite

| कार्य | दोहराने से पहले जाँचें |
| ------ | ------------------------------------ |
| लिंक | डिफ़ॉल्ट अलग परिणाम; suffix, output folder और मूल खिसकाना देखें |
| अवधारणा | सक्रिय backlinks मौजूदा नोट में जुड़ सकते हैं; duplicates अलग हैं |
| शीर्षक जनरेशन | पात्र स्रोत में लिखकर खाली complete destination में ले जाता है |
| अनुवाद | मिलता अनुवाद overwrite हो सकता है; सामान्य नाम `_<language>.md` |
| Mermaid / सूत्र | चुने नोट बदलते हैं; छोटा नमूना और बैकअप रखें |

साझा skip/append/replace विकल्प नहीं है। व्यस्त complete destination स्थानांतरण रोकता है, उससे पहले हुआ generation नहीं। Generated और moved की गिनती अलग है।

### Concurrency

नमूना सफल होने तक `batchConcurrency: 1` रखें। कुछ paths को `enableBatchParallelism` भी चाहिए; translation अपना concurrency मान सीधे लेती है। अधिक parallelism provider, memory और server दबाव बढ़ाता है, गति की गारंटी नहीं। request/group intervals सभी account quotas या अन्य clients का दबाव नहीं हटाते।

## सेटिंग्स

| सेटिंग | प्रारंभिक मान | प्रभाव |
| --------- | --------- | -------- |
| `batchConcurrency` | `1` | लागू batch paths पर माँगी concurrency |
| `enableBatchParallelism` | `false` | समर्थित parallel scheduling |
| `batchSize` | `50` | समूह schedule का आकार |
| `batchInterDelayMs` | `1000` | scheduled समूहों के बीच विराम |
| `apiCallIntervalMs` | `500` | concurrent API scheduling का अंतराल |
| `folderTaskIncludeSubfoldersMode` | `legacy` | हर कार्य का पुराना subfolder दायरा बनाए रखना |
| `enableStableApiCall` | `false` | स्पष्ट stable request mode |

### बैच मॉडल

संबंधित एकल फ़ाइल कार्य का route अपनता है। निजी डेटा से पहले देखें। Title batch का local retrieval आरंभ की एक snapshot रखता है; बीच में हुए edits बाद के results में नहीं मिलते। उन्हें शामिल करने को नया बैच शुरू करें।

## उदाहरण

दो title notes वाला `trial-titles` बनाएँ। **Batch generate from titles** चलाकर सामग्री, साथ वाला `trial-titles_complete` और generated/moved/error संख्या देखें। विफल फ़ाइल अलग जाँचें। मूल फ़ोल्डर दोहराना केवल अधूरे काम का सटीक auto-resume नहीं है।

## Cancel और recovery

नया scheduling रुकता और समर्थित requests को cancel मिलता है। बाहरी सिस्टम के स्वीकार किए calls/writes पूरे हो सकते हैं; शुल्क provider के नियंत्रण में है। समाप्ति के बाद outputs तथा recovery/conflict paths की तुलना करें और recovery फ़ाइलें तब तक रखें।

## सुझाव

- Profile के वास्तविक matches सत्यापित करें।
- 429 में concurrency घटाकर quota देखें।
- Cancel, failure और completion अलग रखें।
- बदलाव से पहले untouched sample और backup बनाएँ।
